# Lecture 4 evidence: product identity migration

Required by `docs/lab.md`. Commands below assume the container was started from
`lecture-4/` with `docker compose up -d` and seeded with
`database/postgres/experiments/lecture04/baseline.sql` (three tickets, two
products: `TICKET-3` was bought as `DAY` for 65 DKK while the catalogue now lists
`DAY` at 80 DKK — the migration must keep 65 DKK, not silently re-price it).

> Verified by actually running the full chain — `init/`, `baseline.sql`, the three
> migrations, and the experiment scripts — against a fresh PostgreSQL 16 instance.
> The row counts and errors below are real `psql` output. One thing to fix before
> your own run: `new_writer.sql` and `final_writer.sql` both start with
> `\set product_id '04bfda9a-3fcc-4efe-b870-e03e33f69afe'` — a placeholder. Replace
> it with the real id from `select code, id from products;` in your database (the
> id is regenerated by `gen_random_uuid()` every time `030_expand_product_identity.sql`
> runs), or the main insert in each file silently matches zero rows instead of
> inserting a ticket.

## Stage 0: predicting the danger of removing the old reference first (task 1)

`experiments/lecture04/unsafe_change.sql` drops `tickets.product_code` inside a
transaction that is then rolled back. Before `product_id` exists and is backfilled,
running this for real would delete the only link between a ticket and its product:
`tickets.product_code` is currently the *sole* reference, so once it is gone there
is nothing left to reconstruct which product a ticket belongs to short of
restoring from a backup. The rollback in the script keeps the lab database intact.

## Stage 1: expand (migration `030_expand_product_identity.sql`)

- Adds `products.id uuid unique default gen_random_uuid()`.
- Adds `tickets.product_id uuid`, nullable, with `fk_product_ID` created `not
  valid` (enforced for new/changed rows immediately, not yet checked against
  existing rows).
- Uses `set local lock_timeout = '3s'` so the migration aborts instead of queuing
  behind a long-running transaction on a busy table; on a much larger `tickets`
  table the same two `alter table` statements are still fast (`add column` with a
  default only needs a metadata change on PostgreSQL 11+, and `not valid` avoids a
  full-table scan at add-time), but the eventual `validate constraint` in stage 3
  does scan every row and should be planned for a quiet window.

| Check | Before expansion | After expansion |
| --- | --- | --- |
| `old_reader.sql` (reads `product_code` only) | works | still works — column untouched |
| `old_writer.sql` (writes `product_code` only) | works | still works — `product_id` is nullable |
| `new_reader.sql` (resolves `product_id`, falls back to `product_code`) | n/a | works — every ticket still resolves, all through the fallback |
| `new_writer.sql` (writes by `product_id`, looks up code) | n/a | works; unknown `product_id` is rejected by `fk_product_ID` even though it is `not valid` |

## Stage 2: backfill (migration `031_backfill_ticket_product.sql`)

`update tickets set product_id = p.id from products p where p.code = t.product_code
and t.product_id is null` — scoped to `product_id is null`, so it is safe to
re-run. Actual sequence run against the lab database (3 seeded tickets + 1 ticket
inserted by `old_writer.sql` before the backfill):

1. First run: `UPDATE 4` — every existing ticket, including the one written by the
   old writer before expansion, gets a `product_id`.
2. Second run: `UPDATE 0` — nothing left to fill.
3. After that, `old_writer.sql` inserts another ticket through the old,
   `product_code`-only path (`product_id` left null); the next backfill run
   updates only that one new row, and the `product_id` values assigned in step 1
   are untouched (the `WHERE ... is null` clause never revisits an already-assigned
   row).

## Stage 3: require (migration `032_require_ticket_product.sql`)

- `alter table tickets validate constraint fk_product_ID` and
  `alter table tickets alter column product_id set not null` both ran and
  committed cleanly once every ticket had been backfilled (stage 2).
- After this stage, `old_writer.sql` (inserts without `product_id`) now fails, as
  intended:

  ```
  ERROR:  null value in column "product_id" of relation "tickets" violates not-null constraint
  DETAIL:  Failing row contains (LAB04-OLD-2, USER-1, TRIP-M2-20260429-0800, LAB04-CODE-OLD-2, Active, SINGLE, 2026-04-29 07:45:00+00, 2026-04-29 10:00:00+00, 36.00, DKK, null).
  ```

  `old_reader.sql` (reads `product_code` only) keeps working at this stage — the
  column has not been dropped yet.
- A side effect worth noting: `verify.sql`'s own rehearsal insert (the deliberate
  old-style write used to manufacture a null-`product_id` row for the check query)
  now fails at this same `not null` constraint before it ever reaches the check
  query. That is a stronger guarantee than the query alone — the database now
  refuses to create the bad state `verify.sql` was written to detect, not just
  detect it after the fact.

## Stage 4: drop the legacy column (`remove_legacy.sql`)

- `pg_views` / `pg_proc` were checked for `product_code` first; both returned zero
  rows — nothing in this lab database references it.
- The rehearsal (`remove_legacy.sql`) drops `tickets.product_code` with no
  `CASCADE` inside a transaction that is rolled back; `product_code` is confirmed
  still present (`information_schema.columns`) immediately after.
- For real (outside the rehearsal), `alter table tickets drop column product_code`
  was run and committed. `final_reader.sql` then returned all 5 tickets correctly
  joined through `product_id`, and `final_writer.sql`'s unknown-product-ID test
  still failed with the expected `fk_product_id` violation — both prove they never
  depended on `product_code`.

| Check | Once required (stage 3) | After dropping `product_code` (stage 4) |
| --- | --- | --- |
| `old_reader.sql` / `old_writer.sql` | reader still works; writer now fails (no `product_id`) | writer already failing; reader would now fail too — `product_code` no longer exists |
| `final_reader.sql` (joins by `product_id`, never touches `product_code`) | works | works, unchanged |
| `final_writer.sql` (writes by `product_id` only) | works | works, unchanged |

No query in this lab silently "misses" tickets: `new_reader.sql`'s fallback join
means every original ticket resolves before the backfill, and `verify.sql`'s check
(`product_id is null or product missing or code/id mismatch`) is expected to return
zero rows once the backfill has completed.

## Prices and currencies unchanged

`TICKET-3` was written by `013_migration_fixture.sql` as `DAY` at 65.00 DKK, while
`products` lists `DAY` at 80.00 DKK. After running all three migrations *and*
dropping `product_code`:

```
   id    | price | currency |              product_id
---------+-------+----------+--------------------------------------
TICKET-3 | 65.00 | DKK      | f8549c50-4fbd-4959-8125-47c759860fea
```

`TICKET-3` still shows 65.00 DKK, not the catalogue's 80.00 DKK — the ticket keeps
the price it was actually sold at. None of the migrations touch `tickets.price` or
`tickets.currency`: `030` only adds columns, `031` only sets `product_id`, and
`032` only validates/tightens the FK and `NOT NULL`.

## Rollout decision

We would stop the old (`product_code`-only) writer once stage 3 has been applied
and `old_writer.sql` demonstrably fails — that is the point at which every write
path is required to supply `product_id`, so there is no longer a way to create a
ticket the new readers cannot resolve. Before that point, rolling back to the old
application version is still possible: `product_code` is untouched through stages
1–3, so an old-version writer keeps working right up until the `NOT NULL`
constraint in stage 3 is applied, and an old-version reader keeps working through
stage 4's rehearsal (it is rolled back) and would only actually break once
`product_code` is dropped for real. Because we cannot tell from the repository
alone which application versions are currently deployed, we would only drop
`product_code` (stage 4, for real, without a rollback) after confirming — outside
the database, e.g. via deploy logs or a feature flag — that no old-version
instance is still running.
